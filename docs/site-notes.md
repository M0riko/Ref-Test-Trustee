# Розвідка сайту trustee.io (Site Notes)

## Як передається реферальний ключ
1. **Сховища (Cookies, LocalStorage, SessionStorage):**
   - Явного збереження ключа під зрозумілими назвами (наприклад, `ref`, `referral`) не виявлено.
   - Ключ не лежить у відкритому вигляді у сховищі.
   
2. **Просування ключа по сайту (Internal Links):**
   - Сайт використовує скрипт, який динамічно (після завантаження сторінки) дописує реферальний параметр `?r=...` до **всіх внутрішніх посилань** (`<a href="...">`).
   - Наприклад, перехід на `trustee.io/cryptocard` автоматично стає `trustee.io/cryptocard/?r=TEST_KEY_123`.
   - Це дуже надійний механізм для навігації в межах домену.

3. **Кінцеві посилання (App Store / Google Play):**
   - Посилання на App Store (`apps.apple.com/...`) та Google Play (`play.google.com/...`) **не містять** ключа безпосередньо в атрибуті `href` після роботи скриптів сторінки.
   - Оскільки за умовами завдання монітор повинен "лише читати href після роботи сайту", і якщо там ключа немає — це вважається втратою (потенційний баг сайту, який наш монітор має успішно виявляти і репортувати як `FAIL_LOST`).

## Висновок для архітектури монітора
Монітор (Краулер) буде працювати так:
1. Заходить на сторінку через Playwright (з `waitUntil: 'networkidle'`).
2. Дає сторінці 1-2 секунди на відпрацювання всіх JS-скриптів.
3. Зчитує всі `<a href="...">`.
4. Внутрішні посилання відправляє в чергу для подальшого краулінгу (залежно від лімітів).
5. Зовнішні посилання на App Store / Google Play перевіряє на наявність ключа (якщо немає — генерує помилку `FAIL_LOST`).
