# 🔍 Trustee Referral Monitor

Автоматизована система моніторингу реферальних ключів для [trustee.io](https://trustee.io).

Монітор симулює поведінку реального користувача (Desktop, iOS, Android) за допомогою браузера Playwright, обходить сайт і перевіряє, чи реферальний ключ `?r=` доходить до кінцевих кнопок завантаження в **App Store** та **Google Play** — не губиться під час навігації.

---

## 🚀 Швидкий старт

```bash
# 1. Встановіть залежності
npm install

# 2. Встановіть Playwright браузер
npx playwright install --with-deps chromium

# 3. (Опціонально) Налаштуйте змінні середовища
cp .env.example .env
# Відредагуйте .env (HEALTHCHECK_URL та MAX_PAGES)

# 4. Запустіть монітор (результат: report.html + status.json)
npm start
```

Після запуску відкрийте `report.html` у браузері — там знайдете повний звіт.

## 📊 Як працює перевірка

### Компоненти
| Файл | Роль |
|---|---|
| `src/crawler.js` | BFS-обхід сайту, знаходить усі сторінки `trustee.io` та `trusteeglobal.eu` |
| `src/extractor.js` | Парсить посилання на App Store, Google Play, `.apk`, смарт-лінки |
| `src/scenarios.js` | 7 сценаріїв перевірки (S1–S7) |
| `src/checker.js` | Головний оркестратор: паралельний запуск, Healthchecks.io пінги |
| `src/storage.js` | SQLite БД: runs, pages, checks, consecutive\_failures |
| `src/reporter.js` | Генерує `report.html` та `status.json` |

### Пристрої (3 профілі на кожну сторінку)
- 🖥️ **Desktop** — Windows Chrome 120
- 📱 **iOS** — iPhone 13
- 🤖 **Android** — Pixel 5

### Сценарії (S1–S7)
| ID | Назва | Що перевіряє |
|---|---|---|
| S1 | Навігація з root | Захід з ключем → клік по внутрішньому лінку → перевірка store-лінок |
| S2 | Прямий візит | Вхід на сторінку одразу з `?r=KEY` |
| S3 | Перезавантаження | S2 + F5 — чи ключ виживає після reload |
| S4 | Ланцюгова навігація | Root → Сторінка A → Сторінка B — multi-hop |
| S5 | Заміна ключа | Старий ключ → новий ключ, старий має зникнути |
| S6 | Контроль (без ключа) | Вхід БЕЗ ключа — переконуємося, що чужий ключ не з'являється |
| S7 | Спецсимволи | Ключ `T_E-S.T~K` — перевірка на подвійне URL-кодування |

### Статуси результатів
| Статус | Значення |
|---|---|
| `PASS` | Ключ коректно передається в store-лінк |
| `FAIL_LOST` | Ключ відсутній у store-лінку |
| `FAIL_ALTERED` | У store-лінку чужий ключ |
| `FAIL_STALE` | Старий ключ лишився після заміни |
| `NO_STORE_LINK` | Сторінка не має кнопок на Store (інформаційно) |
| `INCONCLUSIVE` | Не вдалося перевірити (таймаут, помилка мережі, тощо) — **окремий блок** у звіті, не рахується як успіх |

## 🤖 Автоматизація (GitHub Actions)

Файл `.github/workflows/monitor.yml` щодня о **03:00 UTC** автоматично:
1. Запускає монітор (`npm start`)
2. Завантажує `report.html` та `status.json` як артефакти (30 днів)
3. Якщо виявлено `FAIL` — Workflow отримує статус **Failed** (червоний ✗ на GitHub)

**Ручний запуск:** GitHub → Actions → Daily Referral Monitor → Run workflow.

## 🩺 Перевірка працездатності монітора

### 1. GitHub Actions badge
Перевірте що Workflow "Daily Referral Monitor" зелений — це означає, що останній запуск успішний.

### 2. `status.json`
```json
{
  "run_status": "COMPLETED",
  "overall": "PASS",
  "consecutive_failures": 0,
  "finished_at": "2026-09-22 03:07:41"
}
```
- `consecutive_failures > 0` → щось пішло не так, потрібна перевірка.
- `run_status: "FAILED"` → монітор впав під час виконання.
- `overall: "FAIL"` → монітор запустився, але знайшов проблеми на сайті.

### 3. Healthchecks.io (Heartbeat monitoring)
Налаштуйте безкоштовний акаунт на [healthchecks.io](https://healthchecks.io):
1. Створіть новий Check з `Period = 1 day`, `Grace = 2 hours`
2. Скопіюйте ping-URL у змінну `HEALTHCHECK_URL` (у `.env` або GitHub Action Secrets)
3. Якщо монітор не запуститься понад ~26 год — Healthchecks.io надішле алерт на email.

```
Моніторинг виглядає так:
  Запуск → POST /start   (HC.io знає, що run почався)
  Успіх  → POST /        (HC.io підтверджує: run завершився OK)
  Збій   → POST /fail    (HC.io надсилає алерт)
```

## 🧪 Самоперевірка монітора (Mock Server)

Щоб **довести**, що монітор ловить баги (а не просто малює зелені галочки):

```bash
# Термінал 1: запустіть сервер, що імітує баг (ключ губиться на /broken)
npm run start:mock

# Термінал 2: запустіть монітор проти цього сервера
npm run test:mock
```

Очікуваний результат: `FAIL_LOST` на сторінці `/broken` (де ми навмисно не додали ключ до посилання на Google Play).

## 🐛 Знайдені баги на trustee.io

| Проблема | Платформа | Деталі |
|---|---|---|
| Ключ не передається в store-лінки | 🖥️ Desktop | На Desktop сайт показує кнопку "Google Play", але реальна href веде або на `.apk` (пряме завантаження) без `?r=`, або на Google Play без ключа. JS-скрипт сайту не дописує `?r=` до store-лінок в десктопному режимі |
| Мобільний варіант працює | 📱🤖 iOS/Android | На мобільних сайт використовує смарт-лінки `app.link`, які коректно передають ключ |

## ⚠️ Обмеження

1. **GitHub Actions cron** може запізнюватися на кілька хвилин — для критичного продакшену рекомендується VPS + systemd timer
2. **CAPTCHA та JS-блокування**: якщо сайт додасть CAPTCHA або агресивне bot-detection, частина перевірок стане `INCONCLUSIVE`
3. **Динамічні ключі**: ключ `WoEs9XIVB6b` використовується як тестовий; реальна валідність ключа не перевіряється — лише факт передачі
4. **Пряме завантаження `.apk`**: Playwright не виконує реальне завантаження файлу; монітор перевіряє лише `href` посилання, не вміст файлу
