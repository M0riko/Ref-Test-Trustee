# Trustee Referral Key Monitor

Автоматизований QA-монітор, який перевіряє передачу реферального ключа (`?r=KEY`) сайтом Trustee на кінцеві сторінки крамниць застосунків (App Store, Google Play) через усі внутрішні переходи.

## Як це працює

1. **Краулер (`crawler.js`)**: Знаходить всі внутрішні сторінки сайту (до `MAX_PAGES` та `MAX_DEPTH`).
2. **Чекер (`checker.js`)**: Проганяє **9 сценаріїв** для кожної сторінки під **4 профілями пристроїв** (Desktop Chrome, Mac Safari, iOS, Android).
3. **Storage (`storage.js`)**: Зберігає всі статуси та деталі перевірок у SQLite базу.
4. **Репортер (`reporter.js`)**: Генерує зручний візуальний звіт `report.html`.
5. **Нотифікатор (`notifier.js`)**: Відправляє підсумок або повідомлення про помилки в Telegram.

### Статуси
- **`PASS`**: Ключ успішно дійшов до сторінки магазину.
- **`FAIL_LOST`**: Ключ загублено під час навігації або не додано до посилання магазину.
- **`FAIL_STALE`**: Сайт закешував старий ключ і не замінив його на новий.
- **`FAIL_ALTERED`**: Ключ був змінений (наприклад, з'явився там, де його не очікували).
- **`NO_STORE_LINK`**: На сторінці відсутні посилання на App Store або Google Play.
- **`NO_INTERNAL_LINK`**: Не знайдено посилання на цільову сторінку під час ланцюгової навігації.
- **`STOP_CHAIN`**: Ланцюгова навігація перервана, бо немає лінку для наступного кроку.
- **`INCONCLUSIVE`**: Мережева помилка, таймаут або неможливість завантажити сторінку (перевіряється з retry).

## Як запустити локально

1. Встановіть залежності:
   ```bash
   npm install
   npx playwright install --with-deps
   ```
2. Створіть файл `.env` на основі `.env.example`:
   ```bash
   cp .env.example .env
   ```
3. Запустіть моніторинг:
   ```bash
   npm start
   ```
   *Це запустить монітор (`checker.js`), а потім згенерує звіт (`reporter.js`).*
4. Відкрийте `report.html` у вашому браузері.

## Самоперевірка інструмента (Selftest)

Інструмент містить влаштований механізм самоперевірки (`selftest.js`), який піднімає локальний `mock-server.js` і тестує монітор на ньому, підтверджуючи, що він правильно виявляє всі 4 статуси (PASS, FAIL, INCONCLUSIVE, NO_INTERNAL_LINK).
```bash
npm run selftest
```
Цей скрипт обов'язково виконується у GitHub Actions на кожен push та Pull Request.

## Обмеження

- **Anti-bot захист (Cloudflare)**: Якщо паралельність (limit=6) призводить до блокування, збільште `CRAWLER_DELAY_MS`.
- **WebKit замість Safari**: На Windows/Linux тестується через рушій WebKit. Нативні баги iOS Safari можуть не завжди відтворюватися 1 в 1.
- **OneLink / Appsflyer**: Редиректи перевіряються через NodeJS (HEAD запити). Якщо сервіс блокує Node-fetch, ключ може не знайтись (`FAIL_LOST`).
- **Затримка Cron**: Заплановані через GitHub Actions запуски (cron) можуть стартувати із затримкою до 1 години. Це нормальна поведінка платформи GitHub.
- **Ефемерність GitHub Actions**: Файл бази даних `db.sqlite` вилучено з репозиторію. У результаті, історія запусків (runs) та кількість підряд невдалих запусків (`consecutive_failures`) існують лише в межах одного запуску GitHub Actions runner'а і не зберігаються між днями. Для незалежного контролю "живий/мертвий" монітор шле пінги на Healthchecks.io. Детальні звіти за кожен день залишаються доступними протягом 30 днів як артефакти в GitHub Actions.

## Утиліти розробки
У папці `scripts/dev/` знаходяться розвідувальні та дебаг-скрипти, які не є частиною основного монітора, але використовувалися під час розробки:
- `scratch-dom.js` — тестування Playwright-селекторів.
- `recon.js`, `test_flows.js` — перевірки поведінки редиректів та флоу.

## Чеклист ручної перевірки за ТЗ (A–G)
Щоб впевнитись, що монітор відповідає вимогам ТЗ, ви можете виконати таку перевірку:

1. **A. Crawl (maxPages = 300, maxDepth = 10)**
   - Змініть `CRAWLER_MAX_PAGES` в `.env` на 10. Запустіть `npm start`. Перевірте лог або звіт — монітор має обійти не більше 10 сторінок і записати в лог переривання (Crawl Errors).
2. **B. Redirects (без браузера)**
   - Запустіть `npm run mock`. Змініть `TARGET_URL=http://localhost:3000` в `.env`. Переконайтесь, що звернення до стор-лінків розв'язуються на льоту, не завантажуючи їх у Playwright.
3. **C. Devices (WebKit)**
   - Відкрийте файл `status.json`. Зверніть увагу на блоки `desktop_mac` та `mobile_ios` — вони використовують WebKit, а не Chromium.
4. **D. Selftest & Artifacts**
   - Запустіть `npm run selftest`. Він підніме mock-сервер і самостійно переконається, що баги (втрата ключа, старий ключ) відловлюються як `FAIL_LOST` та `FAIL_STALE`. У `.github/workflows/monitor.yml` цей тест працює автоматично на кожен PR.
5. **E. Scenarios (S4 Ланцюг, S1 Клік)**
   - У звіті `report.html` ви побачите окремі рядки для `S1` та `S4`. Якщо посилання на наступний крок відсутнє, буде статус `NO_INTERNAL_LINK` або `STOP_CHAIN`.
6. **F. Reporter & Screenshot**
   - У HTML-звіті (`report.html`) при наведенні на `❌ FAIL` з'являється Tooltip, де вказані причини помилки (Expected vs Actual) і є клікабельне посилання `📸 View Screenshot` на збережений скріншот у папці `screenshots/`.
7. **G. Notifier (Escape HTML)**
   - Перевірте файл `src/notifier.js` (`notifyFailure`) — помилки очищуються (`.replace(/</g, '&lt;')`) перед надсиланням у Telegram через `<code>` блок, щоб уникнути падіння парсера Telegram API.
